# Phase handoff and evidence continuity

Use the existing project format when adequate. For a material transition, record the phase goal and participants, previous phase, source revision plus dirty state, current requirements, actual outputs/evidence, unresolved issues, and rebuild/run/stop/recovery entry points relevant to the next contributor.

Keep the project timeline distinct from reusable capabilities. One capability can draw on several phases; one phase can produce several lessons. Credit actual contributions rather than the number of skill files or model conversations. Technical labels do not imply permanent ownership by a teammate.

Keep stable case identifiers. Later evidence supports, narrows or contradicts a prior conclusion through an explicit link instead of rewriting the historical observation. Compare environment, inputs, requirement and measurement changes before resolving a disagreement. Mark missing source, raw logs or exact artifact binding rather than inventing them.

For intake, the next contributor may read full historical conclusions and reproduce the needed baseline. That is a handoff check, not an independent migration test when the answer is already known. For a fresh test, freeze input and candidate identity before evaluating, and retain the observed decisions/output.

Scale the record to the work. A small reversible edit may need only its diff and relevant verification. A deployed or concurrent system can need artifact identities, service/ownership state and a recovery receipt. Do not create a release ceremony or mandatory multi-agent process for every edit.

When the user changes or withdraws a goal, preserve what actually happened, the current state and the authorized restore scope. Do not report a partially restored directory as a verified baseline or continue a canceled test automatically.
